CONTRIBUTE TO THE BENCHMARK

Make your result reproducible.

A model repository, a pinned checkpoint, and a verifiable run under the selected benchmark’s rules.

01

Adapt inference

Create your own repository with the core as a root-level submodule. Implement full-batch inference and per-slot reset. Download the pinned author checkpoint and convert it locally when required. Preserve the author's deployment behavior.

Adapter guide ↗
02

Run the whole suite

Use one checkpoint and the fixed protocol. Keep outputs outside Git. Retain full pose traces, source and checkpoint hashes, independent CPU verification receipts and original-inference parity evidence.

Read the evaluation protocol →
03

Request review

Open an issue linking your adapter and external result artifacts. Include the actual submitter, source/checkpoint versions, training-data overlap and any adaptations.

A small adapter. A shared kernel.

MotionChallenge-your-model/
├── MotionChallenge-Core/  # pinned core submodule
├── tensor_adapter.py  # batched policy inference
├── convert_weights.py # original checkpoint conversion
├── runtime.mjwarp.json # clocks, artifacts, input contract
├── admission.mjwarp.json # observation and inference checks
├── provenance.json    # author release and source evidence
├── validation/        # parity and verification receipts
├── evaluate.py        # shared core entrypoint
├── pyproject.toml
└── uv.lock

The core owns datasets, physics, metrics and verification. Model repositories do not copy or override evaluation logic. Checkpoints, data and results live in local caches or external artifact storage.

Propose another benchmark

Specify the robot, observation contract, control frequency, physics and scoring configuration. Publish a dataset manifest with immutable source revisions, file hashes, frame rate, joint order and the complete motion set. Define a distinct protocol version and benchmark identity. Preserve difficult clips, document licensing and overlap, and keep scores in their own track.
